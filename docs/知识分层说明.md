# 知识分层说明：偏好 / 规则与口径 / 文档资料

> 给同事讲这套系统时最常被问的一句是："这些知识不都是'记住'吗，为什么分三块？"
> 这篇就是回答这个问题的。

---

## 1. 为什么必须分层

智能体要"懂业务"，靠的是三种性质完全不同的信息，它们的**生效时机、共享范围、出错后果**都不一样：

| 信息 | 例子 | 本质 |
|---|---|---|
| 你喜欢怎么被回答 | "金额一律用万元""回答用表格" | **服务偏好**，只跟你有关 |
| 业务上什么是"对的" | "主推类目 = M003838,车抵" | **口径**，全组必须一致 |
| 依据是什么 | 《2023 天津统计公报》PDF | **证据**，要看原文和页码 |

如果合成一块，会遇到三个绕不过去的问题：

1. **塞不下**：文档几十万字，每轮都塞给模型 token 直接爆掉；而偏好只有几十字，不塞又记不住。
2. **会串**：偏好是私人的，规则和文档可能要共享给全组。放一张表里，权限没法表达。
3. **错了不知道错在哪**：偏好写错只是"看着别扭"；口径写错是**结论错**；文档索引没做好是**证据缺失**。三种故障的排查和修复方式完全不同。

所以拆成三层，各用各的机制。

---

## 2. 三层一览

| | 个人偏好 | 规则与口径 | 文档资料 |
|---|---|---|---|
| 界面上在哪 | 个人设置 → 偏好 | 知识库 → 规则与口径 | 知识库 → 文档资料 |
| 存哪 | MySQL `pa_user_prefs` | MySQL `pa_knowledge` | PostgreSQL `kb_doc` / `data_kb_nodes`（pgvector，LlamaIndex 管理） |
| 归属 | **只属于本人** | 个人 / 共享（管理员可建共享） | 个人 / 共享 |
| 内容形态 | 一句话，讲**回答方式** | 一句话事实 + 关键词 | 整份 PDF/Word/Excel/PPT |
| 上限 | 单条 300 字，每人 10 条 | 单条 500 字，每人 50 条 | 单文件 20MB |
| 生效方式 | **每轮无条件注入**（≤500 字） | **命中关键词才注入**（≤3 条 / ≤800 字） | 模型**主动检索**，返回原文片段 + 页码 |
| 谁来写 | 你说"记住…"模型写，或自己在设置里加 | 手写一条，或 `remember_fact` | 上传文件，自动解析索引 |
| 索引耗时 | 无 | 无 | 几秒（扫描件 20 秒/页 OCR） |
| 错了怎么修 | 改/删那条偏好 | 改那条规则（含关键词） | 看状态列 → 点重建 |

**一句话记法**：偏好管**怎么说**，规则管**什么算对**，文档管**依据在哪**。

## 3. 一层一层说清楚

### 3.1 个人偏好（pa_user_prefs）

- **只在"回答方式"上用**：格式（表格/分点）、单位（万元/亿元）、语气、篇幅、语言。
- **全量注入，不做检索**：每轮把最多 500 字拼进消息，所以"不会检索漏"，但也不能写多——写十条格式要求会互相打架，还挤占上下文。
- **显式写入**：只有用户明确说"记住/以后都…"，模型才写；模型不许自己揣测偏好默默写入。
- **敏感信息拦截**：内容含"密码/口令/身份证/银行卡/密钥"直接拒收。
- **不进历史摘要**：对话摘要在写入时会过滤掉"要求用表格"这类行，保证偏好只有"本轮注入"一个来源（否则你改了偏好，历史摘要里的旧要求还会生效）。

### 3.2 规则与口径（pa_knowledge）

- **短事实 + 关键词**。关键词决定它什么时候被召回：
  > 内容：主推类目 = M003838,车抵　关键词：M003838,主推,车抵
  问"主推类目 8 月逾期"时命中"主推"，这条被带进本轮上下文。
- **召回上限 3 条 / 800 字**：宁可少带，避免干扰模型判断。
- **两种范围**：`user`（本人）/ `global`（全公司共享，只有管理员能写）。
- **有有效期字段**（`expires_at`）：企业口径会变，过期就不该再生效。
- **权威性排序**：注入时明确写了"与实时查询冲突时以工具查询结果为准"——规则是提示，不是真理。

### 3.3 文档资料（RAG）

- 上传 → 解析 → 切分（按页面/句子，带页码和小节）→ 嵌入（1024 维）→ 存 pgvector。
- 检索是**模型自己决定**要不要调 `kb_search`：向量 + 关键词（RRF 融合）取 top-k，返回片段和出处，模型回答时要标页码。
- **必须给出处**：这是它和"规则"最大的区别——文档是证据，答完要能翻到原文核对。
- 扫描件自动走 OCR（无文字层的页才调视觉模型，20 秒/页，结果缓存）。

## 4. 一次完整对话，三层同时起作用

用户问：**「我们主推类目 8 月逾期多少？」**

```
① 个人偏好   「金额用万元、回答用表格」        → 决定"怎么输出"
② 规则与口径 关键词"主推"命中 → 主推=M003838   → 决定"查哪一类"
③ 文档资料   模型调 kb_search → 命中《8月资产包说明.pdf》第 3 页
                                              → 决定"口径出处"
④ 回答       万元表格 + 「口径见第 3 页」      → 可核对、可追责
```

轨迹里能看到本轮注入了什么（`kind=context`），排查"为什么这次答偏了"时非常有用。

## 5. 关键设计决策（为什么这么定）

| 决策 | 理由 |
|---|---|
| 偏好不做向量检索，全量注入 | 偏好总共 500 字，检索反而会漏；全量最稳 |
| 规则用关键词而不是向量 | 可解释、零依赖、出错能一眼看出是关键词没写对 |
| 规则限 3 条 / 800 字 | 实测注入越多，模型越容易被无关信息带偏 |
| 文档走 RAG 而不是全量注入 | 几十万字塞不进上下文；且必须能回溯页码 |
| 文档索引用独立进程 | 扫码件 OCR 20 秒/页，同步跑会占死 uvicorn worker |
| 上传即触发索引（无定时器） | 定时器最早是"夜里批量"设计，导致上传后几小时才可用；现在上传立刻起后台 worker，实测 3 秒可用 |
| 显式写入（不许模型自动归纳） | 记忆一旦被自动写入脏数据，用户很难发现和清理 |

## 6. 现场演示建议（10 分钟）

**演示 1：偏好（15 秒见效）**
1. 在对话里说："记住：金额一律用万元，回答用表格。"
2. 刷新页面 → 个人设置 → 偏好，能看到这条。
3. 新开一个会话，随便问个带金额的问题 → 表格 + 万元。
4. 删掉这条偏好，再问一次 → 恢复默认（演示"可撤销"）。

**演示 2：规则与口径（讲关键词的作用）**
1. 知识库 → 规则与口径 → 加一条：
   内容「主推类目 = M003838,车抵」，关键词 `M003838,主推,车抵`。
2. 问："主推类目有哪些？" → 模型直接答出 M003838（关键词"主推"命中）。
3. 把关键词改成 `M009999`，再问同样问题 → 这次不会被带进去（**这是最有说服力的一幕**：规则不是"记住就永远生效"，而是"相关时才生效"）。

**演示 3：文档资料（讲出处）**
1. 传一份 PDF，盯着状态列：`排队中 → 解析中 → 索引中 → 可用`（实测几秒）。
2. 问一个只有文档里才有答案的问题 → 回答带页码。
3. 点「重建」→ 演示索引可重来；点「删除」→ 数据干净移除。

**演示 4：三者一起**
按第 4 节的例子走一遍，最后打开轨迹看"本轮注入了：偏好 / 业务知识 / 检索片段"。

## 8. 排错对照

| 现象 | 大概在哪一层 | 怎么查 |
|---|---|---|
| 回答格式不对（该用表格没用） | 偏好 | 个人设置里有没有那条；是不是超了 10 条 |
| 答了错的业务口径 | 规则 | 关键词写对没有；是不是命中不了；`expires_at` 是否过期 |
| 说"没找到相关资料" | 文档 | 文档状态是否 `可用`；检索框直接用原文词试一次 |
| 答对了但没给出处 | 文档/提示 | 看检索是否命中；`kb_search` 返回的片段是否为空 |
| 文档一直"排队中" | 文档 | worker 是否被 kill；点「重建」立刻重跑 |
| 文档 `failed`，提示需要 OCR | 文档 | 扫描件；确认 OCR 网关已配 |
