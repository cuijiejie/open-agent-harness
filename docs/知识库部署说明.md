# 知识库（文档 RAG）部署说明

主系统跑起来之后**可选**加的一块：让智能体能检索上传的 PDF / Word / Excel / PPT。
走的是「pgvector + 本地嵌入模型 + 混合检索（向量 + 关键词）」，**文档不出内网**。

整体只有三个进程：

```
主服务（uvicorn）──HTTP──> 嵌入服务（127.0.0.1:5110，独立进程，只占一份模型内存）
      │
      ├── PostgreSQL（kb 库 + pgvector 扩展，存 chunk 和向量）
      └── 索引 worker（解析→切分→嵌入→写库，夜里定时跑）
```

> 嵌入模型**必须独立进程**。塞进 uvicorn 的 4 个 worker 里会各加载一份模型，内存直接翻 4 倍。

---

## 1. 装 pgvector

PostgreSQL 14 官方源不带 pgvector，源码编译最快（约 1 分钟）：

```bash
sudo apt-get install -y build-essential postgresql-server-dev-14
cd /tmp && curl -sSL -o pgvector.tar.gz \
  https://codeload.github.com/pgvector/pgvector/tar.gz/refs/tags/v0.7.4
tar xzf pgvector.tar.gz && cd pgvector-0.7.4
make -j4 && sudo make install
# 验证
ls /usr/lib/postgresql/14/lib/vector.so
```

## 2. 建 kb 库

```bash
sudo -u postgres psql -c "CREATE DATABASE kb;"
sudo -u postgres psql -d kb -c "CREATE EXTENSION IF NOT EXISTS vector;" \
                      -c "CREATE EXTENSION IF NOT EXISTS pg_trgm;"
```

表不用建，第一次索引/访问时自动建（`kb_doc` / `kb_chunk` / `kb_task`）。

## 3. 起嵌入服务

模型跑在独立环境里，主服务只通过 HTTP 调它。

```bash
# 独立 conda 环境（别装进主环境，onnxruntime 会和主服务抢内存）
"$HOME/miniforge3/bin/conda" create -y -n oah-embed \
    --override-channels -c conda-forge python=3.12
"$HOME/miniforge3/envs/oah-embed/bin/pip" install -q -r requirements-embed.txt

# 先手动跑通（首次会下载模型，约 300MB）
cd /opt/open-agent-harness
HF_ENDPOINT=https://hf-mirror.com \
EMBED_MODEL=sentence-transformers/paraphrase-multilingual-mpnet-base-v2 \
EMBED_THREADS=4 \
PYTHONPATH=. "$HOME/miniforge3/envs/oah-embed/bin/python" -m src.kb_embed_server \
    --host 127.0.0.1 --port 5110
```

另开一个终端验证：

```bash
curl -s localhost:5110/health
# {"ok":true,"embedding_model":"...","dim":768,...}

curl -s localhost:5110/embed -H 'Content-Type: application/json' \
     -d '{"texts":["天津市2023年地区生产总值"]}' | head -c 120
```

> **模型选择有个坑**：`fastembed==0.4.2` 里**没有** `BAAI/bge-base-zh-v1.5`；
> `bge-small-zh-v1.5` 的权重只放在 Google Storage（国内拉不到）。
> 实测可用且是 768 维的是 `sentence-transformers/paraphrase-multilingual-mpnet-base-v2`。
> 想换别的模型，先 `TextEmbedding.list_supported_models()` 看名字和维度，**维度必须和配置里的 `dim` 一致**。

**重排要不要开？没有 GPU 就关掉。** 实测（8 核 CPU）：

| 场景 | 嵌入延迟 | 内存 |
|---|---|---|
| 只加载嵌入模型（`RERANK_MODEL=none`） | **0.32 s/次** | 约 600MB |
| 同时加载重排 `bge-reranker-base` | **8 s/次**（两个模型抢 CPU） | 打满 2G |

而且 20 段重排要 3.2 秒，而检索侧的重排超时只有 200ms，等于白占资源。所以 CPU 机器上：

```bash
# systemd unit 的 [Service] 段里加（注意别写到 [Install] 下面，会被忽略）
Environment=RERANK_MODEL=none
```

有 GPU 或机器够强时再去掉这行；重排加载要 20~30 秒，服务在后台线程预热，不会挡查询。

### 装成 systemd 服务

```bash
sudo cp deploy/pa-kb-embed.service /etc/systemd/system/
# 按实际路径改 WorkingDirectory / ExecStart（默认写的是 /opt/open-agent-harness）
sudo systemctl daemon-reload && sudo systemctl enable --now pa-kb-embed
systemctl status pa-kb-embed --no-pager
```

## 4. 配主服务

**4.1 `config/configs.cfg` 的 `[kb]` 段**

```ini
[kb]
enabled = true
pg_db = kb
embed_url = http://127.0.0.1:5110
dim = 768                # 必须和嵌入模型的实际维度一致
max_file_mb = 20
data_dir =               # 留空 = <仓库>/data/kb（OCR 缓存也在这里）
```

**4.2 `.env`**

```bash
# kb 库和主库同一实例、同一个 postgres 账号时可以不写（自动复用 [agent] 的 pg 口令）
PA_KB_PG_PASS='PG密码'

# 只用得上扫描件 OCR 才需要（见 §6）
PA_KB_OCR_API_KEY='视觉网关的key'
```

前缀规则：`.env` 变量名是 `PA_` + **section 名大写** + 配置项名，所以 `[kb] pg_pass` → `PA_KB_PG_PASS`。

**4.3 重启并验证**

```bash
sudo systemctl restart open-agent-harness     # 服务名以 install.sh 装的为准
curl -s -b cookies.txt http://127.0.0.1:5001/open-agent-harness/api/kb/stats
```

期望：

```json
{"ok":true,"docs":0,"chunks":0,"failed":0,"pending":0,
 "embed":{"ok":true,"detail":{"dim":768,"embed_error":"","rerank_error":""}}}
```

`embed.ok=false` 说明主服务连不上 5110，先看嵌入服务日志。

## 5. 索引怎么跑（上传即触发，无需定时任务）

上传只做两件事：存文件、写一条 `kb_task`。真正的解析/切分/嵌入在**独立进程**里跑，
不会占住上传请求（扫描件 OCR 要 20 秒/页，30 页就是 10 分钟）。

触发点有三个，都在代码里，不用配 cron：

| 触发 | 说明 |
|---|---|
| 上传成功 | 接口立刻调 `systemd-run --unit=pa-kb-index-now` 起一次性 worker |
| 点「重建」 | 同上（重新解析、重新嵌入） |
| 服务启动 | 若队列里有 `pending`，启动时补跑一次（部署/重启不丢任务） |

固定 unit 名保证**同一时刻只有一个 worker**；多人同时上传时后来者被 systemd 拒绝，
正在跑的那个 worker 会把任务表里的新任务一起捡走（`FOR UPDATE SKIP LOCKED` 防重复）。

手动跑一批（调试用）：

```bash
cd /opt/open-agent-harness
PYTHONPATH=. "$HOME/miniforge3/envs/oah/bin/python" -m src.infra.kb.ingest --once
```

查看 worker 日志：`journalctl -u pa-kb-index-now -n 50 --no-pager`（Popen 兜底时写在 `data/kb/ingest.log`）。

> 页面上状态会依次变化：`排队中 → 解析中 →（扫描件）OCR 识别中 → 索引中 → 可用`，
> 失败的会写明原因。**没有定时器**，所以卡住的文档点「重建」就会重跑；
> worker 被 kill 导致任务停在 `running` 时，10 分钟后会被下一个 worker 当僵尸任务重新捡起。

## 6. 扫描件 OCR（可选）

没有文字层的扫描 PDF，默认会 `failed` 并写明"需要 OCR"。要支持就接一个
**OpenAI 协议的视觉接口**（`/chat/completions` + `image_url`）：

```ini
[kb]
ocr_enabled = true
ocr_base_url = https://你的视觉网关/v1
ocr_model = 你的视觉模型名
ocr_dpi = 150          # 150 够用；调高更清晰但更慢
ocr_max_pages = 30     # 超过的页不 OCR，防止几百页扫描书打满网关
ocr_timeout_s = 120
```

```bash
PA_KB_OCR_API_KEY='sk-xxx'      # 写进 .env
```

工作机制：

| 情况 | 行为 |
|---|---|
| 页面有文字层（≥40 字） | 直接用 PDF 里的文字，**不调模型** |
| 页面无文字层 | 渲染成 PNG → 视觉模型 → 文本 |
| 识别结果 | 缓存到 `data/kb/ocr/<doc_id>/p<页码>.txt`，重索引不重复调用 |
| 单页失败 | 跳过继续下一页；**一页都没成功**才整篇 failed |
| 耗时 | 实测约 **20 秒/页**（150dpi，中文统计公报） |

## 7. 验收清单

```bash
B=http://127.0.0.1:5001/open-agent-harness
curl -s -c /tmp/ck -o /dev/null -X POST -d 'username=admin&password=admin' $B/login
curl -s -b /tmp/ck $B/api/kb/stats                                    # embed.ok=true
curl -s -b /tmp/ck -F 'file=@/tmp/测试.pdf' -F 'scope=user' $B/api/kb/docs   # 上传
curl -s -b /tmp/ck "$B/api/kb/docs?limit=20"                          # 看 status/chunks
curl -s -b /tmp/ck --get --data-urlencode 'q=文档里的问题' --data 'top_k=3' $B/api/kb/search
```

界面上：**知识库 → 文档资料**，能上传、能看到状态、能被"检索"命中。

## 8. 排查

| 现象 | 原因 / 处理 |
|---|---|
| 启动报 `type "vector" does not exist` | 没装 pgvector 或没在 `kb` 库里 `CREATE EXTENSION vector` |
| `/api/kb/*` 全 404 | `[kb] enabled = false` |
| `embed.ok=false` | 5110 没起；看 `systemctl status pa-kb-embed` |
| 写库报 `expected 768 dimensions` | 换了嵌入模型但 `dim` 没改，或旧数据维度不同 → 改 `dim` 后重建索引 |
| 文档一直 `embedding` | worker 被 kill；点「重建」立刻重跑（或等 10 分钟僵尸回收） |
| 文档 `failed` 且提示 `需要 OCR` | 扫描件；按 §6 配 OCR |
| 文档 `failed` 且提示 `PostgreSQL text fields cannot contain NUL` | 老版本 bug，已修（解析层去控制字符） |
| `rerank_error: Model '' is not supported` | 重排没配模型，属正常降级（不报错，只是排序略差） |
| 检索"答得上但排序不理想" | 未启用重排；或文档太多需要把 `top_k` 调大 |

## 9. 卸载 / 清理

```bash
sudo systemctl disable --now pa-kb-embed pa-kb-index.timer
sudo -u postgres psql -c "DROP DATABASE kb;"       # 所有向量和文档记录
rm -rf /opt/open-agent-harness/data/kb             # 原始文件 + OCR 缓存
# configs.cfg 里 [kb] enabled = false 即可让接口和 kb_search 工具失效
```
